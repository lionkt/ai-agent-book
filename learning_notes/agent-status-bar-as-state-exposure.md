# Agent 状态栏：不是文件系统，而是状态暴露机制

## 问题

书中第 2.6 节的“Agent 状态栏”，本质上是不是类似 File System：通过文件系统追踪 Agent 的状态？

可以把它理解成额外的一块小黑板，用来记录任务、追踪完成情况，以及保存当前状态吗？

## 核心结论

“小黑板”这个理解是对的，但 Agent 状态栏不等于 File System：

> File System 解决“状态存在哪里”，Agent 状态栏解决“怎样把当前状态主动暴露给模型”。

底层状态可以保存在文件、进程内存、数据库或工作流引擎中。状态栏的关键能力不是“写文件”，而是由 Harness 把分散的状态整理成紧凑的当前快照，并在模型做下一次决策时显式提供。

## 为什么需要状态栏

在 Agent 的执行过程中，状态通常分散在很长的 trajectory 中：

```text
第 3 轮：模型制定计划
第 7 轮：完成第一个步骤
第 12 轮：某个测试失败
第 18 轮：修复完成
第 23 轮：重新运行测试
```

模型理论上可以回看这些历史，但要判断“现在进行到哪里”，就必须重新完成一次归纳：

- 原计划有多少项；
- 哪些已经完成；
- 最近一次错误是什么；
- 下一步应该做什么；
- 工具调用额度还剩多少。

随着 history 增长，这种临时归纳越来越不稳定。模型擅长从上下文中检索某条已知信息，但不擅长每轮都从大量事件中稳定地计算全局状态。

因此，Harness 会提前把分散在轨迹和环境中的状态整理成当前快照：

```xml
<agent_status>
  <goal>修复登录超时问题</goal>
  <progress completed="2" total="4"/>
  <next_step>运行回归测试</next_step>
  <last_error>test_refresh_token failed</last_error>
  <tool_calls used="12" limit="30"/>
  <working_directory>/repo/auth</working_directory>
</agent_status>
```

模型在进行下一次决策时直接读取这份快照，不必重新扫描和统计完整历史。

## 状态栏的四层结构

状态栏可以拆成四层：

```text
状态来源
  工具结果、Todo、执行计数、环境信息
                ↓
状态存储
  进程内存、File System、数据库、工作流引擎
                ↓
状态整理
  Harness 计算进度、筛选最新异常、生成紧凑快照
                ↓
状态暴露
  把快照注入当前上下文，供模型下一步决策
```

三个核心动作是：

```text
记录状态 → 整理状态 → 暴露状态
```

File System 只覆盖“记录状态”的一种实现。Agent 状态栏的核心价值主要在后两个动作。

## File System 只是存储后端之一

一种实现方式是把状态保存在文件中：

```text
.agent/state.json
        ↓
Harness 读取并整理
        ↓
<agent_status>...</agent_status>
        ↓
注入模型上下文
```

也可以完全不落盘，直接保存在进程内存中：

```python
runtime_state = {
    "goal": "修复登录超时问题",
    "completed_steps": 2,
    "total_steps": 4,
    "last_error": "test_refresh_token failed",
}
```

存储方式取决于状态的生命周期：

| 场景 | 更合适的存储方式 |
| --- | --- |
| 单进程、短生命周期 session | 进程内存 |
| 需要崩溃恢复或断点续跑 | 文件或数据库 |
| 多 Agent、跨进程共享 | 数据库或工作流引擎 |
| 需要人工查看和编辑 | 文件、任务系统或数据库界面 |

只有当这些状态被 Harness 整理并主动提供给模型时，它们才真正发挥状态栏的作用。单纯把状态写进文件存在几个问题：

- 模型可能忘记读取；
- 模型可能读到旧版本；
- 每次重新读取都需要额外的工具调用；
- 模型不知道状态何时已经变化、什么时候应该重读。

## 状态栏更像 HUD，而不是工作日志

完整工作日志记录整个过程：

```text
10:01 启动任务
10:03 读取配置文件
10:05 第一次测试失败
10:08 修改代码
10:10 第二次测试通过
```

汽车 HUD 只展示当前驾驶最需要的信息：

```text
当前速度：80 km/h
剩余油量：35%
导航下一步：500 米后右转
```

Agent 状态栏也是一样：

```text
当前进度：2/4
下一步：运行回归测试
最近错误：refresh token 测试失败
剩余工具调用：18
```

因此，它不是另存一份完整 history，而是把长历史整理成模型此刻决策所需的高密度状态视图。

## 与 Skill、Memory 和存储后端的区别

```text
Skill：
我应该怎样完成这类任务
——操作手册，提供流程性知识

状态栏：
这个任务现在进行到哪里
——实时仪表盘，提供当前工作状态

Memory：
过去形成了哪些值得长期保留的信息
——持久记忆，服务未来任务

File System / 内存 / 数据库：
上述信息实际保存在哪里
——存储后端，不直接定义信息的语义
```

可以进一步压缩成：

```text
Skill 管“怎么做”
Status 管“做到哪”
Memory 管“以后还要记住什么”
Storage 管“这些信息存在哪里”
```

## 最终心智模型

> Agent 状态栏是一块由 Harness 维护并主动展示给模型的小黑板。底层状态可以保存在内存、File System、数据库或工作流引擎中；关键能力不是“写文件”，而是把任务进度、环境状态和执行约束整理成当前快照，并在模型做下一次决策时显式提供。
