# Context Engineering 的本质及其与 ICL 的关系

## 1. 问题

Context Engineering 的本质是什么，它在解决什么结构性问题？它和上下文学习（In-Context Learning，ICL）是什么关系？Agent 状态栏、RAG、上下文压缩等技术又是否都属于 ICL？

## 2. 核心结论

> **Context Engineering 是在每个模型决策点，把外部世界中与当前决策有关的状态，投影成一个有限、清晰、足以支持行动的 token 观测。**

它要解决的根本问题不是“Prompt 写得不够好”，而是：

> **真实任务状态不等于模型可见状态。**

在这条链路上，Context Engineering 和 ICL 分属系统侧与模型侧：Context Engineering 控制“模型看见什么”；ICL 是模型在参数不变时，根据看见的指令和示例临时改变行为的能力。

## 3. 结构性问题：模型并不身处任务环境

一次 LLM 调用可以抽象为：

```text
a_t ~ pi_theta(. | C_t)
```

部署后模型参数 `theta` 基本固定。模型在当前决策点只能依赖输入 `C_t`，并不能直接看见数据库中的最新订单、文件系统状态、工具调用产生的真实副作用、团队没有写下来的业务规则，以及哪些信息已经过期。

设系统可访问的完整任务状态为 `X_t`，Context Engineering 负责构造模型可见的上下文：

```text
C_t = E(X_t, H_t, K, T, B)
```

其中 `H_t` 是执行历史，`K` 是外部知识，`T` 是工具定义，`B` 是 token、延迟和成本预算。Context Engineering 真正设计和运行的是投影函数 `E`。

它的目标不是让 `C_t` 尽量接近 `X_t` 的完整副本，而是让模型仅凭 `C_t` 作出的决策，尽可能接近看到完整状态时的决策：

```text
P(a_t* | C_t) ~= P(a_t* | X_t)
```

因此，好的 context 不是“信息尽可能多”，而是关于当前决策的近似充分统计量。这个充分性是任务相关的：同一份完整状态，在不同决策点需要投影出的信息并不相同。

## 4. Context Engineering 在弥合什么鸿沟

真实状态进入模型，需要连续跨过三道鸿沟。

第一，许多信息根本不在模型上下文中。最新数据存在数据库，任务进度存在 Workflow Engine，文件内容存在文件系统。RAG、工具调用和状态读取先解决“模型看不见”。

第二，系统可以访问的信息远大于上下文窗口。即使能够全部塞入，日志、旧历史和无关材料也会稀释注意力。检索、Skills、截断和压缩解决“看不完”。

第三，原始信息的形态未必适合决策。三次电话调用散落在几十轮历史里，模型虽然“看过”，却仍需重新检索、去重和计数。状态归约、结构化摘要和权限标记解决“看见了但不能可靠使用”。

完整的数据流是：

```text
外部真实状态
    ↓ 获取
候选信息
    ↓ 选择、归约、标注权限与时效
决策相关状态
    ↓ 序列化
模型上下文 C_t
    ↓
模型决策
    ↓
新事件写回外部状态
```

Context Engineering 管理的是这个随任务推进不断更新的循环，而不只是某一次 Prompt 的文字。Prompt Engineering 主要优化指令如何表达，属于 Context Engineering 的一个局部组件；RAG、工具定义、对话历史、Skills、状态栏和上下文压缩都参与构造 `E`。

Context Engineering 也不能凭空创造模型能力。如果必要事实没有进入上下文，换更强的模型通常也无法知道；如果事实已经完整清晰，模型仍不会做精确计算，则应使用代码工具、训练或更强模型。可以据此区分问题所在：

```text
不知道必要事实       → Context Engineering 问题
找到事实但组织混乱   → Context Engineering 问题
事实清晰但不会推理   → 模型、工具或训练问题
知道答案但无法执行   → Harness、Tool 或权限问题
```

## 5. Context Engineering 与 ICL 的关系

二者位于同一条链路，但不在同一层：

```text
任务与环境状态
      ↓
Context Engineering
选择、压缩、组织并更新上下文
      ↓
模型实际看到的 C_t
      ↓
模型读取事实、遵循指令、推理，或通过 ICL 适应任务
      ↓
下一步动作 a_t
```

当上下文中的指令或示例发生变化，模型无需更新 `theta` 就表现出新的任务行为，这种推理时的临时适应才是 ICL。

### 5.1 工程分类上的包含，不等于机制上的包含

从工程技术分类看，few-shot 示例的选择、排列和注入属于 Context Engineering；但从内部机制看，ICL 是模型消费这些示例时表现出的能力。两者是“供给—消费”关系：

```text
Context Engineering：选择哪些示例，以什么顺序、放在什么位置
ICL：从这些示例中推断当前任务的映射或规律
```

Context Engineering 的范围远大于 ICL，因为模型使用上下文不只有“从示例学习”这一种方式：

| Context Engineering 操作 | 模型主要在做什么 | 是否属于典型 ICL |
| --- | --- | --- |
| 注入 few-shot 输入输出示例 | 推断任务映射 | 是 |
| RAG 注入事实证据 | 检索并使用事实 | 通常不是 |
| 注入工具定义 | 理解当前可执行动作 | 不一定 |
| 注入 Agent 状态栏 | 读取状态并应用规则 | 不是 |
| 压缩历史为结构化摘要 | 使用更紧凑的事实表示 | 不是 |

因此，不能把“模型利用了上下文”一概称为 ICL。检索事实、读取状态、遵循显式规则和基于上下文推理，都可以发生在没有任务模式学习的情况下。

## 6. 状态栏在这套关系中的位置

状态栏是典型的 Context Engineering，而不是典型的 ICL。

假设原始轨迹中散落着三次对商家 A 的电话调用。没有状态栏时，模型需要从历史中找出相关事件、去重、计数，再判断是否达到上限。状态栏由 Harness 预先维护：

```text
merchant_A.call_count = 3
```

模型随后只需读取这个状态并应用“最多调用三次”的规则。这里没有从示例中学会新任务；Context Engineering 改变的是模型的观测表示，把原本需要在线归纳的隐式状态变成可以直接使用的显式状态。

用数据库类比：

```text
原始 Agent 轨迹       → event log
每轮让模型重新统计    → query-time aggregation
Harness 维护状态栏    → materialized view
```

这里还要区分状态存储与上下文投影：

```text
状态存储      → 事实保存在数据库、文件、内存或任务系统中
上下文投影    → 当前有哪些事实需要暴露给模型
模型内部表示  → 模型读取 context 后形成的临时激活和 KV Cache
```

Context 不是事实的最终存储，也不是世界本身，而是模型在当前决策点拿到的一张有限切片。外部状态才是 source of truth；状态栏只是为当前决策生成的视图。

## 7. 对书中“上下文学习”的术语校准

书中前面对 ICL 的定义较接近通常口径：模型不重新训练，仅凭输入中的指令和示例适应新任务。但在“上下文学习的内部机制：检索而非推理”一节中，讨论范围已经扩大到长上下文检索、轨迹统计和摘要使用，实际谈的是 **context utilization**，不只是狭义 ICL。

因此，更严谨的表述是：

> **Context Engineering 负责把任务所需的信息变成模型可用的观测；ICL 负责从其中的指令和示例推断临时任务规律。检索、状态读取和上下文推理与 ICL 并列，都是模型消费 context 的方式。**

三者可以用一句话区分：

```text
训练改变模型参数；Context Engineering 改变模型观测；ICL 让固定参数的模型根据观测临时适应任务。
```
